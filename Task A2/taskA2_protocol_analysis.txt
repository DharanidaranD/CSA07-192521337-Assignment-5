A2.1 E-MAIL
SMTP session (client C, server S):
 S: 220 mail.learn.example ESMTP ready
 C: EHLO student-pc.learn.example          S: 250-mail.learn.example / 250-STARTTLS / 250 OK
 C: MAIL FROM:<student@learn.example>      S: 250 2.1.0 Sender OK
 C: RCPT TO:<faculty@learn.example>        S: 250 2.1.5 Recipient OK     (550 if mailbox does not exist)
 C: DATA                                   S: 354 End data with <CR><LF>.<CR><LF>
 C: Subject: Doubt ... body ... <CRLF>.<CRLF>   S: 250 2.0.0 Message queued
 C: QUIT                                   S: 221 Bye
Reply classes: 2xx success, 3xx need more input, 4xx temporary failure (retry), 5xx permanent failure.
POP3 (download-and-delete) on phone, laptop and lab PC: whichever device connects first downloads the mail and
deletes it from the server; the other devices never see it, read/unread state and folders are not shared, and
deleting/archiving on one device is not reflected on others; the mail in a shared lab PC is also left on a public
machine. IMAP keeps messages and folders on the server; devices synchronise flags (read/answered/deleted), folders
and can fetch headers first and bodies on demand, plus IDLE push. So all three devices show the same mailbox.

ALTERNATIVE: webmail (HTTPS) vs IMAP client, mailbox of 50 messages (assumptions: average 40 KB message, 1 KB headers)
 IMAP client: SELECT + FETCH of envelopes/flags ~ 50 x 1 KB = ~50-100 KB; bodies fetched only when opened.
 Webmail: first load of the web application (HTML/JS/CSS) ~ 1-2 MB (cached afterwards) + JSON list ~ 50-100 KB.
 -> First open: IMAP ~0.1 MB vs webmail ~1.5 MB; later opens are similar (~0.1 MB). 
 Security: webmail is easier to secure centrally - one HTTPS endpoint, MFA, WAF, no client config; IMAP needs IMAPS/
 STARTTLS on port 993/143, app passwords and exposes another login port to brute force.

A2.2 FILE TRANSFER AND MONITORING
 Active FTP: client opens control connection (client:port -> server:21) and tells server its data port with PORT;
 the SERVER then opens a new connection from port 20 to the client. A firewall/NAT in front of clients blocks this
 unsolicited inbound connection. Passive FTP: client sends PASV, server returns a port, and the CLIENT opens both
 connections outbound - firewall allows outbound; the server only needs a defined passive port range open.
 Why SFTP/HTTPS: FTP sends passwords and data in clear text and needs many ports; SFTP (SSH, port 22) and HTTPS
 (443) encrypt everything, use a single port, and are firewall friendly.
 SNMP: manager sends GetRequest(ifInOctets.2) to router UDP/161 (community/SNMPv3 user); router replies
 GetResponse with the Counter32 value. Utilisation % = (delta octets x 8) / (interval x ifSpeed) x 100.
 TRAP: when a link fails the router sends an unsolicited Trap/linkDown (OID 1.3.6.1.6.3.1.1.5.3) to the manager on
 UDP/162, no polling needed (InformRequest if acknowledgement is required).

A2.3 DNS AND HTTP TIMINGS (browser developer tools -> Network -> Timing)
 DNS Lookup high -> slow resolver / no caching; Initial connection + SSL high -> far server, handshake RTTs;
 Waiting (TTFB) high -> slow server/back-end; Content Download high -> low bandwidth/large page; Stalled/Queueing
 -> too many requests per connection. A slow page with long DNS and Connect but short TTFB is a network/DNS problem
 (fix: closer server/CDN, better resolver); long TTFB is a server problem.
