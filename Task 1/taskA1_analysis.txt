TASK A1 - WHERE DOES THE DELAY COME FROM?
(Calculations reproduced by delay_and_bdp_calculations.py)

A1.1 DELAY BREAKDOWN
Assumptions: 3 routers => 4 links, store-and-forward (packet is fully transmitted on every link);
signal speed in fibre = 2 x 10^8 m/s.
  Transmission: L/R = 1500x8 / 100x10^6 = 0.12 ms per link x 4 links = 0.48 ms
  Propagation : d/v = 2,000,000 / 2x10^8                       = 10.00 ms
  Queuing     : 3 routers x 0.5 ms                               = 1.50 ms
  Processing  : 3 routers x 0.1 ms                               = 0.30 ms
  TOTAL                                                          = 12.28 ms
Dominant component: propagation (10 / 12.28 = 81%).
Upgrade to 1 Gbps: transmission falls to 0.048 ms, total 11.848 ms - a saving of only 0.43 ms (3.5%).
Judgement: not worth it for latency; propagation is fixed by distance (physics), so the cure is to move the
content closer (regional servers/CDN) and to cut queuing (QoS). More bandwidth helps throughput, not delay.
(If a single link is assumed, transmission is 0.12 ms and total 11.92 ms - same conclusion.)

A1.2 BANDWIDTH-DELAY PRODUCT
  BDP = 1 Gbps x 80 ms = 80 Mbit = 10 MB (about 9,766 KiB) - the data "in flight" needed to keep the pipe full.
  A TCP sender can have at most one window unacknowledged per RTT:
  Throughput_max = W / RTT = (64 x 1024 x 8 bit) / 0.080 s = 6.55 Mbps = 0.66% of 1 Gbps.
  The sender sends 64 KB, then idles ~80 ms waiting for ACKs. Fix: TCP window scaling (RFC 7323) with a window
  >= 10 MB, or parallel connections.

A1.3 TARGETS AND TOOLS
Application       | One-way delay | Jitter   | Loss   | Throughput          | Main tool
Live video (class)| < 150 ms      | < 30 ms  | < 1 %  | 1.5-4 Mbps/stream   | Wireshark RTP analysis, iperf3 UDP
Voice (VoIP)      | < 150 ms      | < 30 ms  | < 1 %  | 80-90 kbps/call     | Wireshark RTP, ping (RTT/jitter), Packet Tracer
Recorded video    | seconds OK    | n/a (buffered) | < 2 % (TCP recovers) | >= 5 Mbps per HD stream | iperf3 TCP
E-mail            | seconds-mins  | n/a      | 0 (TCP) | tiny (kbps)       | SNMP counters, Wireshark
File download     | not critical  | n/a      | < 0.1 % | as near link rate as possible | iperf3 TCP, SNMP utilisation
Path/hop problems | -             | -        | -      | -                   | traceroute
Design/what-if    | -             | -        | -      | -                   | Packet Tracer / NS-3
Active measurement  = inject test traffic (ping, traceroute, iperf3); measures what you ask for, any time, but adds load.
Passive measurement = observe real traffic (Wireshark capture, SNMP counters); no extra load, shows real users'
experience, but only when traffic exists.

ALTERNATIVE CONCEPT ANALYSIS - passive only
 Obtainable: link utilisation and throughput (SNMP ifInOctets/ifOutOctets), packet loss & retransmissions and
 jitter for existing RTP flows (Wireshark), RTT of TCP flows (from SYN/ACK timing), error/discard counters.
 Missed: delay or loss on idle paths, one-way delay (needs both ends), maximum available capacity (iperf3),
 path/hop breakdown (traceroute), behaviour of a new site/continent before users arrive.
 When noticed: only after users are already affected (evening frozen video) - reactive. SNMP polls every 1-5 min
 hide short bursts. Best practice: passive for continuous monitoring + active probes for baselines and capacity.
